# 実装計画・タスク分割（コーディングAI向け）

- 文書バージョン：1.0
- 目的：一括生成を避け、各段階でビルド可能・検証可能な状態を維持する。
- 正の仕様：`anonymous_terraria_server_spec.md` と `requirements.json`。API検証は `anonymous_terraria_api_validation_matrix.md`、DBは `database_design.md` を参照。

## 0. 開発の進め方

- プラグインを巨大な一括実装で書かない。各フェーズでコンパイル・テスト・差分確認を行う。
- Criticalな技術検証が未通過の機能に対し、本体ロジックを推測で実装しない。必要なら隔離された最小技術スパイクで調査する。
- 各タスクの出力は「変更ファイル」「実行したビルド／テスト」「結果」「未解決事項」にまとめる。
- 失敗を隠さない。ビルドできない状態で次フェーズへ進まない。
- 仕様を満たす代替手段が必要な場合、勝手にスコープを変更せず、根拠・影響・代替案を記録する。

## 2. タスク詳細と成果物

### P0 — 環境・仕様の棚卸し

作業：
- `requirements/`と`docs/`の配置および現在のファイルを確認する。
- 実際に使用するTShock配布物のバージョン、Terrariaバージョン、OTAPI、.NET SDK／ランタイム、OS／CPUアーキテクチャを確認する。
- `TerrariaServer.dll`、`TShockAPI.dll`、OTAPI／その他参照DLLの実ファイルの場所とアセンブリバージョンを調べる。
- 公式リリース一覧を再確認しても、使用者が持つ実物DLLと違うものを想定して進めない。
- 実装用ディレクトリ、ビルド方法、テストサーバー、既存Discord連携の所在を記録する。

完了条件：`environment_baseline.md`を作成し、事実・推測・未入手ファイルを分ける。秘密情報や実運用のパスワードを含めない。

### P1 — 空プラグインのビルドとロード

作業：
- 最小のプラグインプロジェクトと必要な参照だけを作る。
- 参照DLLのバージョンとTargetFrameworkを合わせる。
- 起動／ロード／終了時にログを出すだけの実装とする。
- 本体機能をここへ先行して書かない。

合格：`dotnet build`相当が成功し、テストサーバーの起動ログにロード成功があり、例外なく停止できる。

### P2 — Critical技術スパイク（本体実装前）

スパイクは本体から切り離した短い検証コードとし、ソース・結果・再現手順を残す。

1. **自動ログイン＋SSC**：接続時処理、アカウント生成／紐付け、SSC初期化、再接続復元の順序を確認。手動コマンドなしで参加できること。
2. **ボス制限**：召喚アイテム、自然出現、NPC/イベント生成、派生出現、Lunar系イベント、クライアント要求など全経路をテスト。ロック中の対象が一体も出ないこと。カバーできない経路があればブロッカーとして残す。
3. **タイルイベント**：`TileEdit`/`PlaceObject`等を実動作で調べ、採掘・設置・開花ハーブを二重／欠落カウントせず判定できること。
4. **釣果検出**：普通の魚、箱、ジャンク、クエスト魚、釣りNPCを区別し、成功釣果だけを検出する。実証できなければ「釣り神」は未実装扱いのまま、代替手法を調査する。
5. **報酬受取**：スポーン地点の指定チェストを操作し、通常チェスト動作を抑止して個人別に受取を制御できるかを確認。成立しなければ同じ場所で使う最小限の代替UIを用いる。案内NPCやミッション端末へ拡張しない。
6. **ボス参加**：召喚者・近接・投射物・召喚武器を比較し、AFK滞在のみを除外できる判定方法を確認。
7. **報酬／SSC保存の境界**：付与前・付与後・DB記録前後で異常終了させ、二重付与／消失をどう検出・復旧するか確認する。

完了条件：`anonymous_terraria_api_validation_matrix.md`の各項目に `PASS` / `FAIL` / `BLOCKED` を根拠付きで記入し、CriticalなBLOCKED項目には回避・代替案の設計を記載。テストしていないものをPASSにしない。

### P3 — 基盤：設定・DB・ログ

タスク：
- 設定クラス／JSON読み込みとスキーマ検証。
- SQLite接続、`database_design.md`に基づく初期マイグレーション、FK、一意制約、インデックス。
- 時刻の共通サービス（内部UTC、日次キーJST）。
- 構造化されたプラグインログ。
- `/serverstatus`相当の管理者専用状態確認（コマンド登録方法は実DLLで確認）。

合格：空DB初期化、再起動、マイグレーション失敗、JSON不正、FKチェック、ログ出力がテスト可能。

### P4 — プレイヤー識別とSSC

タスク：
- `players`への内部ID紐付け。
- 実証済みの自動ログイン／内部アカウント処理を実装。
- 表示名変更、切断・再接続、同名の別アカウントをテスト。
- 管理者権限・SSC回避権限の誤付与を確認。

合格：通常参加者が認証コマンドを手入力せず、同じキャラクター・進捗を復元し、別参加者データと混線しない。技術スパイクで成立していない方法をそのまま採用しない。

### P5 — 日次とボス解禁

タスク：
- サーバー開設基準日時と設定スケジュールの読み込み。
- 停止中も進行する解禁計算、再起動時同期、既解禁を再ロックしない処理。
- 日次処理の冪等キー `day_key`。
- すべてのボス解禁ゲートと標準ワールド条件を分離。
- 手動解禁と監査ログ。

合格：時刻を模擬して各日、停止期間、設定変更、手動解禁、標準進行条件のシナリオを通す。

### P6 — 実績イベント計測

タスク：
- ゲームAPIイベントを薄いAdapterに閉じ込め、ミッション／表彰ロジックから直接イベントAPIを呼ばない。
- Adapterは「採掘成立」「設置成立」「ハーブ採集成立」「釣果成立」「ボス参加」等のドメインイベントに正規化する。
- イベント取得不可・対象不明・API検証未合格の場合は加算しない。未検証の数値を推測で埋めない。
- 採掘／設置カウントの二重イベントは、実際のAPI通知の意味を確認して処理する。座標とブロックIDだけの一意キーで、正当な同じ場所の再設置を不当に除外しない。

合格：テストワールドで手動操作の期待値とカウンターが一致する。

### P7 — ミッションエンジン

タスク：
- `mission_candidates.json`の126候補を読込。初期候補は `enabled_by_default: false` を尊重し、全件を自動有効にしない。
- JSONで定義ID、条件、ターゲット、scope、報酬、進行条件、出現重みを扱う。
- 全体／個人進捗と貢献の処理を分離。
- ボス未解禁、ワールド進行不足、入手不能素材の候補を除外。
- 直近3日回避は初期案として設定可能にする。
- 当日選出スナップショットを永続化し、設定再読込で進行中の条件を変えない。

合格：固定選出／候補選出、候補不足、JSON再読込、日次切替、途中参加、重複イベントをテスト。

### P8 — 報酬・デイリー共有報酬

タスク：
- 共通`reward_grants`台帳と決定的idempotency key。
- 個人報酬、全体達成時の対象者別付与待ち、オフライン付与、インベントリ満杯を実装。
- 共有報酬ティアを累積全体達成で上げ、日次リセットで下げない。
- 初期スポーン地点の専用受取機能を実装。対象地点周辺へ建築保護区域を作らない。
- 同じプレイヤー・JST日付の二重claimを一意制約で防ぐ。
- SSC保存と独自台帳の境界で結果が曖昧なケースを`needs_review`にし、自動再配布しない。

合格：連打、同時クリック、切断、再起動、満杯、オフライン、DB障害のテスト合格。

### P9 — 表彰10部門

対象：開拓功労賞、採掘功労賞、建築功労賞、薬草採集賞、富豪、釣り神、物資支援賞、ミッション貢献賞、継続冒険賞、皆勤賞。

タスク：
- 開催期間と判定ルールをスナップショット保存。
- 指標と発見／活動日／ボス参加をサーバー側で集計。
- 富豪は確定時点の個人資産（インベントリ＋対象の個人保管資産）を銅貨相当でスナップショット。オフラインSSC読取が成立するか検証する。
- 皆勤賞はシーズン対象ボスすべてで資格ある戦闘参加履歴がある人を抽出。
- `/award preview`は管理者だけに候補・判定理由・欠損を表示。
- `/award finalize`は同率複数受賞／該当者なし／二重確定防止を含む。
- `/award history`は過去結果を確認。
- 公開発表は賞名・受賞者の匿名表示名のみ。順位、実績値、次点者を公開しない。

合格：各賞のテスト用データから期待結果と一致し、同率・該当者なし・確定再実行・発表失敗が正しく扱われる。

### P10 — 管理者運用・バックアップ

タスク：
- ミッション状況／reload、ボス状況／手動操作、報酬状態／安全な再試行、表彰操作。
- 重要な変更は管理者操作ログに記録。
- SQLiteと設定のバックアップ／復旧、DB整合性確認。
- エラーや処理待ちをログで追跡できるようにする。
- 新しいDiscord botやDiscord連携の改修は追加しない。

### P11 — 統合試験・配布

- `anonymous_terraria_server_spec.md`の受入基準を全件検証。
- 公開用HTML、内部要件、バイナリや秘密情報を適切に分離。
- 本番適用前にワールド・TShock・SSC・プラグインDB・JSONを一体としてバックアップ。
- 更新手順、ロールバック手順、障害時の`needs_review`対応を記載。
- 本番ワールドで検証する前に、テストワールドでボス解禁・報酬・日次更新を通す。

## 3. 受け入れテストの最低条件

次のシナリオを全て実行し、実施結果をテストログとして保存する。

- 初回参加→自動認証→SSC初期化→切断→再接続。
- 表示名変更後も同じ内部プレイヤーIDに進捗が紐付く。
- 日次更新直前／直後、複数日停止後の再起動。
- 同じミッションイベントの重複通知、進捗上限への到達、全体報酬の同時配布。
- ログインボーナス二重クリック／2接続同時／インベントリ満杯。
- 報酬付与前・ゲーム内付与直後・DB確定直前・DB確定後にプロセスを停止するクラッシュ試験。
- 解禁前ボスの召喚アイテム／自然出現／イベント／派生生成等の全試験経路。
- 釣果、開花ハーブ、富豪、各ボス戦参加を実データと照合。
- 表彰の同率、該当者なし、確定後の再実行、結果発表の送信失敗。
- JSON破損、SQLite整合性エラー、バックアップ復旧。
- 既存Terraria⇔Discordチャット連携が従来どおりであること。
- ワールドのブロック設置／破壊制限が新設されていないこと。

## 4. フェーズ完了レポート形式

各フェーズ完了時は、AIは必ず次を短く記録する。

1. 完了したタスクと変更ファイル。
2. 実行したbuild／testコマンドと結果。
3. 仕様要件IDとの対応。
4. 失敗・未検証・代替処理を設けた事項。
5. 次フェーズ開始に必要な前提。

未実行のテストを実行済みと報告しない。コードが存在することだけを「完成」と扱わない。
